# External Job Dispatch Recovery

Use this procedure when a webhook or gateway job dispatch fails, especially when the failure may have occurred before the network request.

## Procedure

1. Identify the intended task ID, current payload, and any superseded task IDs before submission. Mark superseded jobs as isolated from the current run. **Check:** one current task is named and no obsolete task can be mistaken for it.

2. Complete the payload, domain gates, and dry-run before formal submission. Record each result separately because payload validation does not prove transport readiness. When the payload reuses assets from outside the current job, build a dispatcher-readable reference bundle and record each expected asset's identity, size, and digest. Validate the bundle's producer state before reuse: require a successful terminal status, reconcile expected and completed counts, require a zero failure count, and reject any asset that still has a partial-output marker. Resolve the bundle through the same input path the dispatcher will use, then compare the resolved inventory with the payload before submission. When owner input is required, open or identify the host-owned masked credential-entry surface, name the fields to complete without showing their values, and confirm that the surface is editable before handing control over. If the owner cannot enter values there, clarify the same secure surface rather than moving protected values into chat, commands, URLs, or logs. Verify required endpoints and credentials at the actual dispatcher execution boundary with presence-only or masked checks; stored configuration and a `Ready` status do not prove child-process injection. Close the entry surface after verification. If a credential appeared in chat or logs, have the owner rotate it through the host-owned secure path, then verify only that the replacement is present. **Check:** the current task has explicit gate and dry-run outcomes, every reused asset resolves with the expected identity, size, and digest at the dispatcher boundary, the owner can identify where secure input belongs, every required runtime input is present at the execution boundary, the entry surface is closed, and no protected value appears in the record.

3. Submit the current task once through the formal dispatcher and retain its structured result or state artifact. Distinguish payload rejection, pre-network configuration failure, and a request that may have reached the remote service. When validation stops at the first missing prerequisite, report only that prerequisite as proven missing and mark later prerequisites as untested. **Check:** the failure stage and each prerequisite status are classified from dispatcher evidence rather than inferred from the error text alone.

4. Verify side effects before retrying or reporting a dispatch gap. When the task contract defines a deterministic state location, inspect it for artifacts keyed to the current task ID before calling the dispatcher again. Treat `ready_to_submit` and an existing payload without a submission receipt as a transient handoff state, not proof that automation stopped. Re-read the project checkpoint, submission receipt, deterministic task directory, progress artifact, and current owner-session status after the payload writer reaches a stable checkpoint. Treat a progress artifact showing an accepted or active state and matching expected-versus-queued work counts as authoritative submission evidence; cross-check any input-resolution manifest against the intended payload or asset bundle. Report “not submitted,” “not queued,” or “no charge” only when the dispatcher result or submission state proves the request stopped before network activity; otherwise report “dispatch in progress” or mark remote state unknown and reconcile it first. **Check:** the current task ID, stable checkpoint, owner-session state, work counts, and resolved inputs agree across concrete result or state artifacts before any retry or user-facing status conclusion.

5. Preserve a pre-network-blocked task as pending and write a blocker record with the task ID, passed gates, failure stage, and safe resume condition. Keep protected configuration values out of task files and chat; ask the owner to restore them through the host-owned configuration path. **Check:** the blocker contains enough non-secret state to resume without rebuilding the package.

6. After readiness is restored, revalidate the pending task before submission. Reuse its task ID only when the payload is unchanged; issue a new task ID and supersede the old one when the payload changes. **Check:** the submitted ID maps unambiguously to the validated payload.

7. Confirm remote receipt or authoritative submission state before starting dependent work. Record transport receipt, dispatcher confirmation, remote task identity, fixed result location, and remote progress as separate fields so an HTTP acceptance cannot be mistaken for active or completed work. When the formal dispatcher returns HTTP success but no remote task ID, fixed task directory, progress artifact, or dispatcher execution state exists, classify the task as `webhook_accepted_unverified`. Preserve the receipt and local task ID, block duplicate submission and downstream dispatch, and name the authoritative evidence that can promote the task to queued or active; do not report generation as started. Compare queued and completed counts independently: when queued reaches expected but completed remains zero, classify the task as queued and waiting rather than completed. For an accepted asynchronous task with authoritative state, persist its task ID, fixed result location, expected completion evidence, and waiting status. Resolve progress ownership from the actual `session_progress_cards` record rather than session existence or project metadata, then reconcile the visible card from the same submission evidence. When the recorded owner differs from the card-record owner or the card shows an earlier phase, repair the owner reference and visible card before reporting status. **Check:** each status cites its own evidence, an unverified acceptance remains blocked from retry and dependent work, one durable card record proves the canonical owner, the visible card agrees with the latest state evidence, and the record contains enough non-secret context to resume monitoring without redispatching the task.

8. Install a bounded condition watch keyed to the current task, the proven progress-card owner, and the best available authoritative state source. If a durable progress artifact does not exist yet, watch for authoritative state creation or change without treating the submission receipt itself as execution proof. Evaluate durable state without a model turn and wake the owner only when its status signature changes. Publish numeric completed/expected progress without a spinning wait step. Route the terminal callback through the same proven owner, reconcile the final card, and disable the watch after success or failure. Carry the task ID and continuation target in every wake event. **Check:** the watch is active, can detect the first authoritative state after an unverified acceptance, routes to the owner proven by the card record, stays silent when state is unchanged, ignores superseded tasks, publishes changed numeric progress, and disables itself after one terminal reconciliation.

9. On wake or an apparent stop, reconstruct one ordered timeline from the submission receipt, remote progress or terminal evidence, callback ingress result, continuation trajectory, durable project checkpoint, and visible progress card. Classify callback delivery, continuation activity, validation completion, and project persistence separately. Treat an unchanged project checkpoint as processing lag only when callback evidence and a later continuation event prove forward motion; treat a session `running` marker as advisory rather than activity proof. Validate the current task ID, completion marker, and result artifact before continuing. Exit without action when the task is no longer current; continue dependent work only from validated results. **Check:** the timeline identifies the last proven stage, every visible status cites its evidence plane, and one accepted task produces at most one continuation with no duplicate submission.
